# NPC 到 SoC、Linux、顺序双发射与流片的目标路线

> 长期目标：以现有 RV32 五级流水线 NPC 为起点，形成可验证的单发射 SoC 基线；在单发射版本上启动 Linux；加入分支预测，再扩展为顺序双发射并保持 Linux 回归；根据课题组资源选择一个边界清楚的版本完成流片。面向 2027 年集创赛的具体交付，以届时官方赛题、规则和时间表为准。

本文是目标与验收路线，并非当前完成状态报告。旧的 [CPU 阶段笔记](cpu.md)保留 D/E/F 等实现细节；阶段性结果记录在独立验收记录中，例如 [D3 验收](d3-acceptance.md)。每跨过一道关口，都记录 RTL commit、工具与容器版本、配置、测试输入、seed、日志位置和失败清单。

## 1. 当前起点与终点

从当前源码可直接看到：core_top.v 已有五级寄存器、redirect/kill、WB CSR 提交与中断入口；if_stage.v、mem_stage.v 仍用 DPI 访问仿真内存；顶层尚无独立的可综合取指/数据总线端口；csr.v 当前是 M 模式 CSR 子集。D4 的 CSR 冒险仍是待验收项。已有 D3 定向测试只覆盖其列出的场景，不能外推为整核或 Linux 验证通过。

目标产物按依赖关系形成：

| 关口 | 产物 |
| --- | --- |
| P0 | 五级流水线正确性基线 |
| P1 | 可等待、可回压的存储接口 |
| P2 | 总线与最小 SoC，运行裸机程序 |
| P3 | 单发射 Linux 启动基线 |
| P4 | 带分支预测的单发射版本 |
| P5 | 顺序双发射版本，Linux 与裸机持续回归 |
| T | 从 P2/P3/P4/P5 中选一个冻结版本，另做 DFT、物理实现与签核 |

P3 先于 P5，使双发射的每一项改动都有可对照的系统软件基线。Linux 启动不构成所有流片项目的必要条件；T 线的具体冻结版本取决于课题目标、经费、工艺与交付时间。P5 也不自动意味着具备流片条件。

## 2. 在接口固化前写清架构合同

以下是拟定范围，尚未宣称当前 RTL 实现：单 hart、RV32、M/S/U 模式、Sv32、原子指令、Zicsr、Zifencei，以及与所选 Linux 配置匹配的异常、中断、定时器和设备。指令集字符串要按真实实现与所选固件、内核配置确定；A、S/U、Sv32 等不能只写在编译参数中。浮点、压缩指令与自定义扩展列为单独决策，不在未实现时对外承诺。

在 P1 前固定并版本化以下合同：

- **ISA/特权**：支持的扩展与版本；各 CSR 的 WARL、异常优先级、委托、mret/sret、中断屏蔽及恢复规则；未对齐访问策略。
- **提交语义**：每条指令至多提交一次；异常与中断有准确的 epc/cause/tval；被 kill 的 Store/CSR 写不能产生外部可见副作用；为 Difftest 提供动态提交记录。
- **内存与设备**：地址图、ROM/RAM/MMIO、访问宽度、字节使能、错误响应、顺序约束、cacheability，以及 FENCE/FENCE.I/原子操作的系统语义。
- **平台**：复位地址、时钟/复位、UART、定时器/中断控制、调试与固件入口；设备树描述要与实际硬件一致。
- **验证配置**：参考模型、工具链、内核/固件版本、可复现命令与已知豁免；分别统计架构、微架构、性能和安全观察结果。

## 3. 实施关口

| 关口 | 设计与软件工作 | 通过标准及留下的证据 |
| --- | --- | --- |
| **P0 流水线正确性** | 完成 D4 CSR 结果到 GPR、CSR 同地址 RAW；检查 redirect/kill、Store 副作用、ECALL/MRET/中断边界；定义精确异常和提交 trace。 | 定向最小程序覆盖依赖与优先级；现有 D3 回归保持通过；记录第一条错误提交而非仅记录最终状态。未完成项进入 issue 清单。 |
| **P1 可等待存储接口** | 用 IF/MEM 的 req/resp 接口替换综合路径上的 DPI；支持可变延迟、回压、错误与跨阶段 hold；明确 IF 旧请求在 redirect 后的丢弃规则。 | 随机等待、连续请求、redirect 遇等待、Store 仅一次、异常遇等待等检查；lint/仿真可复现。DPI 可以继续留在 testbench 内。 |
| **P2 总线与最小 SoC** | 接总线 bridge/interconnect、ROM/RAM、UART、timer/IRQ；确定地址图、复位和启动链；先运行裸机程序。cache 可按总线吞吐需求分步接入。 | 总线协议断言或监视器、随机回压、MMIO 顺序、异常响应、定时器中断、裸机程序和 Difftest；可综合顶层无 DPI。 |
| **P3 单发射 Linux 基线** | 实现并验证 S/U、Sv32/TLB 与 SFENCE.VMA、委托及 supervisor CSR、页故障、原子操作、timer/SBI、固件、设备树与串口；补齐所选内核配置真正要求的 ISA/平台功能。 | 从固定版本固件启动到内核早期日志、完整 boot log、init/用户态程序；异常/页表/中断/原子定向测试与长时间回归。任何仅出现 boot banner 的状态标为“早期启动”。 |
| **P4 分支预测** | 在单发射基线上加入预测表、更新时机、恢复 PC 和错路状态清除；记录预测命中、错误、代价及面积/时序。 | 同一程序的提交序列与 P3 一致，Linux 回归通过；定向覆盖连续跳转、异常和 redirect 竞争；性能统计可重复。 |
| **P5 顺序双发射** | 定义同拍配对限制、槽间 RAW/控制依赖、双写回仲裁、单/双内存端口约束、顺序提交和精确异常；先保守发射，再逐项放宽。 | 单发射/双发射差分、边界定向、随机程序、Linux 回归；报告 IPC、面积、频率、功耗估算与难以双发射的比例。 |

P3 的启动合同应逐项核对所选 Linux 与 OpenSBI 版本。Linux RISC-V 启动文档要求入口时 a0 为 hartid、a1 为设备树地址、satp=0；OpenSBI 的平台条件与固件适配另行核对。资料：[Linux RISC-V boot](https://docs.kernel.org/arch/riscv/boot.html)、[OpenSBI platform requirements](https://github.com/riscv-software-src/opensbi/blob/master/docs/platform_requirements.md)。

P4/P5 的测量合同：在相同编译器、二进制、存储延迟和频率约束下比较；同时报告正确率、每千条指令 redirect/flush、CPI/IPC、面积及关键路径。Difftest 通过只说明其覆盖的架构状态一致，不能替代访存协议、错路副作用或物理时序检查。

## 4. 流片线 T：课题组投入之前的立项与签核

“能仿真”到“值得投入课题组经费流片”之间有两道不同的门槛：有明确研究/教学交付价值，以及设计能按选定工艺与封装完成可测的硅片。没有统一的“写到 Linux/双发射才可以流片”标准；最终清单由导师、工艺/MPW 项目、PDK、IP 授权和签核流程决定。

### T0：立项冻结

给出 2–4 页可评审项目说明：研究问题或竞赛任务、与现有基线比较的创新点、预计面积/频率/功耗与验证指标、芯片框图、工艺/MPW、die 与封装/IO、存储宏来源、外部 IP 许可、工具/PDK 可用性、人员职责、排期、预算和风险。确定一个可实现的首版范围，例如单发射 SoC 加硬件可观测机制；双发射只有完成 P5 验收且 PPA 允许时才进入首版冻结。经费申请应说明硅后如何测得论文或比赛所需数据，以及失败时仍可交付的 FPGA/仿真结果。

### T1：硅可综合设计边界

明确 core、SoC、testbench 三层。把 DPI 访存留在 testbench；芯片路径使用可综合总线和 SRAM/ROM 宏 wrapper。定义全部时钟、复位、测试模式、异步输入同步、时钟域交叉、引脚和存储器初始化/启动方式；跑综合、lint、CDC/RDC、latch/组合环检查，并保存网表和约束。SRAM 宏、IO/pad、ESD、PLL/时钟源按所选工艺和项目条件处理，不可凭通用 RTL 推断已有这些资源。

### T2：冻结版本的功能验证

按实际 ISA/特权配置运行架构测试、定向异常/中断/存储测试、长程序与提交级 Difftest；用协议检查器和随机延迟验证总线；检查复位、非法指令、错路 Store/CSR 写、cache/TLB 一致性及固件启动。追踪覆盖缺口和豁免。RISC-V [ACT 项目](https://github.com/riscv/riscv-arch-test)能提供架构测试；ACT、Difftest、Verilator 仿真均不是单独的流片签核。

### T3：物理实现与 DFT

根据工艺/MPW 规则执行综合与多角时序约束、floorplan、placement、CTS、routing、寄生参数提取、STA、功耗/IR/EM 检查和版图 DRC/LVS/天线检查；把封装/IO/SRAM 宏纳入相同签核。制定 scan/JTAG、存储器测试或可观测访问、启动/复位测试和硅后测试向量。具体必需项、角点、门槛与可用工具以所选项目的 signoff 文档为准。[OpenROAD flow](https://openroad.readthedocs.io/en/latest/main/README.html)和 [OpenLane 2 flow](https://openlane2.readthedocs.io/en/latest/reference/flows.html)展示了常见开源物理实现与检查环节，但能跑完某个 flow 不等于 foundry 接受签核。

### T4：交付与硅后验证

冻结 RTL/约束/固件/测试程序及哈希，归档签核报告、GDS/网表、引脚/封装文档和已知风险；由项目负责人与工艺方确认提交。上板后先测电源/时钟/复位/串口或调试口，再测指令、异常、中断、内存、温度/电压/频率，最后运行目标应用与论文/竞赛指标。保留硅前后差异记录。

## 5. 近期执行顺序与决策点

1. 先完成并验收 **D4 → P0**：把 CSR RAW、system/IRQ 邻接测试与整核回归整理为可重复入口。
2. 设计 **P1 的 IF/MEM req/resp 合同**，明确可变延迟下的 valid/ready、取消响应和提交副作用；再替换 DPI 综合路径。
3. 完成 **P2 裸机 SoC**，同时建立第一次综合/时序/面积基线，尽早发现流片线的结构性问题。
4. 选择并固定 Linux/OpenSBI/工具链/设备模型版本，拆分 **P3** 的特权、MMU、原子、固件和外设任务。
5. 达成 P3 后依次做 **P4、P5**；每一步保留旧版作为差分与性能对照。
6. 在 P2 后即可与导师评估 **T0**；根据资源在 P2/P3/P4/P5 中选冻结点，预留足够的 T1–T4 时间。竞赛规则发布后把赛题指标映射到具体关口。

每个关口都输出一页验收记录，字段固定为：版本、配置、命令、覆盖场景、通过/失败、首个偏差、PPA、剩余风险与下一关口。这样“完成五级流水线”“能启动 Linux”“具备流片条件”分别有可检查的含义。
